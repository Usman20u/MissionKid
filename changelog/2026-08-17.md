## Plan 03 implementation — Task 1: persisted lifecycle and contract adaptation (F003)

- Widened the one browser-local snapshot to the full Mission Session lifecycle in a single change: a current session in `selected`, `ready` or `active`, a collection of uniquely identified sessions in `completed`, and a current-result pointer that is either null or the identifier of exactly one valid completed session. `snapshotVersion` stays `1`, the namespaced storage key and the single persistence adapter are unchanged, and no migration exists. Snapshots written by the `F001` and `F002` builds still hydrate unchanged and are still writable.
- Modelled the lifecycle as one discriminated union on `state` over shared immutable selection facts. `ready` carries no start timestamp; `active` requires one structurally valid `startedAt` and no completion facts; `completed` requires `startedAt`, a `completedAt` not earlier than it, and one `completionPeriodId` in the approved `YYYY-MM` form. A completed session cannot occupy the current position, a current session and a current-result pointer cannot both be present, and one identifier cannot name both an unfinished and a finished session. Impossible combinations and unknown lifecycle values are refused rather than repaired.
- The stored completion period is validated for shape only and never recomputed from `completedAt`, so a later timezone or clock-context change cannot reassign a period identity that was already fixed.
- Implemented the record-level trust rules for completed sessions: each record is validated on its own, so one unreadable record no longer makes the whole snapshot unreadable; identical duplicate copies coalesce by stable identifier; copies of one identifier that disagree are excluded from counting until a deterministic valid record can be recovered; an invalid current-result pointer is rejected by itself with all valid completions preserved; and an invalid age band leaves completed sessions intact. No read rewrites, trims or reorders the stored entry.
- An otherwise valid `active` session whose `durationSecondsAtSelection` is missing, null, zero, negative or fractional now hydrates as `active` with the stored value preserved exactly, so guidance can degrade to zero without a duration being invented or the family's Mission being discarded. A duration that is not a number at all remains a refusal, and `selected` and `ready` still require a positive whole-second duration.
- Implemented decision D4-B at the persistence boundary: while stored data holds an invalid completed record, or copies of one identifier that disagree, every snapshot-replacing write is refused through the existing unconfirmed result under the new `blocked-completed-record` reason. The stored value is left exactly as it was, nothing is trimmed or chosen as a survivor, the trustworthy completed facts stay readable, the family is told through the existing parent-facing recovery and retry path rather than being shown success, and reset stays a deliberate parent decision. The refusal reads stored data itself, so a caller cannot pass it by supplying a filtered snapshot; a later read in which the condition is absent lets the same write through. ## Plan 03 implementation — Task 5: timer derivation (F003)

- Added the pure derivation of remaining guidance from a running session's own durable facts: its immutable `startedAt` and the duration it froze at selection, with the clock reading passed in. It is total — every input, including a reading that is not a number, yields one typed, bounded result rather than a throw, a NaN, an infinity or an invented timestamp — and the result is always a whole number of seconds between zero and the stored duration. Units are explicit throughout: stored facts are epoch milliseconds and whole seconds, readings are milliseconds.
- Live ticks come from a monotonic anchor rather than from the wall clock: guidance is read once from the timestamps, tied to a monotonic reading, and every later value is that anchor minus the monotonic time elapsed since. Values therefore follow elapsed time rather than the number of callbacks received, so a late, coalesced or throttled tick shows the time that actually passed instead of running slow, and a backward wall-clock adjustment cannot make the live display increase. Where a browser provides no monotonic clock, elapsed time falls back to wall time and is still clamped so it can only hold guidance still.
- Re-anchoring happens on first sight of a running Mission and on every return to the page. It re-reads the durable timestamps, so time that passed while the page was hidden is accounted for by the facts rather than by anything the page counted, and a refresh recovers the running Mission at its real remaining time instead of resetting it to the full duration. Within one page lifetime the value can only fall: a wall clock rolled back to a time still after the start is capped by what the previous anchor's own elapsed time says, and a rollback to before the start reads zero. That ceiling is runtime knowledge for this page only; no counter is stored to hold it.
- Anchors belong to one session identity and to one page lifetime. An anchor naming another session guides nothing, readings from different lifetimes are never compared, and no anchor, tick, deadline or remaining-time value is written anywhere. Language changes, ordinary renders, a repeated start that resolves the same running session, and duplicated focus or visibility events all leave timing exactly as it was.
- Added the runtime wiring the derivation needs: the anchor lives in runtime application state, page returns recalculate it, and a display update is scheduled only while the page is visible and guidance is above zero. At rest — before a Mission is running, at zero, while hidden, and after unmount — nothing is scheduled and no listener remains. A session in `selected` or `ready` has no timer at all.
- Zero stays a resting state: guidance stops at zero, the session remains `active`, and nothing overtime, expiry, failure, automatic completion, abandonment or reward follows from it. A missing, null, zero, negative or fractional stored duration reads zero without the stored value being replaced, a wall clock earlier than the start reads zero, and a structurally invalid start timestamp is reported as an invalid session rather than treated as a trustworthy running Mission.
- No countdown presentation was built: the derivation and its wiring have no rendered consumer yet, which is the plan's own split between this task and the active presentation that follows it. No control, view or handoff was added or changed.

## Plan 03 implementation — Task 7: ready cancellation, confirmed abandonment and conflict resolution (F003)

- Added the one durable operation both non-completion exits share: the current Mission Session is cleared through the existing confirmed-write path. Ready cancellation and confirmed abandonment differ only in what the family had to do to ask for it, so they are one keyed, freshly-read operation rather than two.
- The operation is decided by durable state and the identity the family acted on, together with the lifecycle state they acted from. A cancellation that arrives after the Mission started never abandons a running Mission; an exit never clears a different session, even one holding the same Mission; and a session found in another state, or replaced by another session, is preserved and handed back so the interface follows what is actually stored.
- Leaving adds nothing. No completed record, result pointer, reward, progress source, timestamp, identifier, abandonment history or extra lifecycle state is written, and settings, the child profile, completed sessions and every other snapshot fact are carried across untouched. Neither exit uses the global reset path.
- A completed Mission Session cannot be cancelled or abandoned: the operation refuses an identity that names one, and its completion and result reference are left exactly as they are.
- A repeated exit resolves an already absent session without writing again. Absence is never read as permission to clear whatever is current now, and no path recreates a session that may already be gone.
- Neither exit depends on remaining time, a usable stored duration, or Mission content that still resolves. A family may always stop, including at zero and for a Mission that can no longer be shown.
- Added the ready view's secondary return to suggestions beside the dominant **Start mission**. Nothing has started and nothing is counted, so it asks no further question.
- Added the active view's secondary leave-without-completion control and the confirmation it requires. The confirmation names the action, states that the Mission will not be counted, puts the easy **Keep going** first as the primary choice and keeps **Leave mission** explicit and visually separated. It uses the same calm, restrained surface as the reset confirmation already in the product, carries no guilt, urgency or hidden exit, and is reached from one shared component so both places that offer it ask the identical question.
- The confirmation moves focus to its own heading when the family opens it and returns focus to the control they opened when it is dismissed, by **Keep going** or by Escape. Opening, dismissing and re-opening it change no durable fact, and the Mission keeps running throughout: guidance neither pauses nor restarts while the family decides.
- Resolved the existing-session conflict `F002` surfaced without a control. The conflict now names the current Mission from reviewed catalog content and offers the approved choice: return to that session in whatever lifecycle state it actually holds, or take the non-completion exit that state calls for, with an active Mission still requiring its confirmation. Clearing the conflict returns the family to the suggestions and does not choose the Mission they had asked for: selection stays deliberate.
- While an unresolved conflict stands, no new Mission appears available to choose. The three Missions stay fully readable and only choosing is withheld, through the same native disabled cascade the recovery controls already use, which closes the presentation requirement that a new selection must not appear available until the conflict is resolved.
- Leaving returns to the approved Discovery path with the setup, language and Mission Category context that are already current. The cycle's shown identifiers are not carried back, so an ended cycle is never resurrected, and none of this navigation state is persisted.
- Both failure classes are handled truthfully and in this operation's own words. An established refusal leaves the Mission exactly where it was and says the exit was not carried out; an interrupted write claims neither that the Mission was left nor that it was kept, re-reads durable state, and adopts what it finds — the session gone, the same session still present, or another session to be preserved and followed. No path writes a session back over an exit that may already be durable.
- D4-B is unchanged and is not bypassed to make an exit appear successful: while stored data holds an unresolved completed record, the replacement is refused and the stored bytes are left exactly as they were.
- Ordinary hiding, returning, closing, refreshing and navigation remain nothing of the kind. None of them writes, clears a session or opens a confirmation, and reopening finds the same Mission.
- Changed the conflict notice wording in all three languages. It previously told the family to choose the same Mission again, which was the only route available when no control existed; it now points at the choice the conflict actually offers.
